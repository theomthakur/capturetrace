    From a physical reading to a trusted project value.

    CORE DECISIONS

    Why the system behaves this way

    1. 01
      Store before send

      The app commits locally first. Delivery becomes retryable work, not a one-time hope.

    2. 02
      Retry with the same identity

      A repeated delivery cannot create a second measurement because the event ID does not change.

    3. 03
      Validate at the boundary

      Units and schema versions are checked before a value can enter the form.

    4. 04
      Make uncertainty visible

      Unknown input enters review with a reason. The system does not silently convert or guess.

    SYSTEM NOTES

    What this prototype proves

    01

    Local-first capture

    A capture is assigned an identity and retained before network delivery is attempted.

    02

    Idempotent replay

    The receiver uses the stable event ID to make retry and reconnection safe.

    03

    Contract validation

    Units, field context, schema version, and device metadata are validated at the boundary.

    04

    Human-visible failure

    Anything uncertain enters a review state with a reason instead of disappearing or being guessed.

    Scope boundary

    This is a browser-only simulation. It is not a BLE implementation, production architecture recommendation, or representation of another company's internal system.

    01 / THE QUESTION

    Can a field measurement remain trustworthy when the network and software are imperfect?

    CaptureTrace is a focused reliability sandbox for the moment physical work becomes digital project data.

    02 / THE INVARIANT

    No measurement is silently lost, duplicated, converted, or assigned to the wrong field.

    Stable identityExplicit contextVisible stateSafe ambiguity
    03 / THE FLOW

    Capture locally. Deliver safely. Validate once. Explain every decision.

    Tool→Outbox→Validation→Workflow

    Each stage owns one responsibility, which keeps transport failure separate from data correctness.

    04 / THE SCENARIOS

    Five situations expose five distinct system behaviors.

    05 / THE DECISIONS

    The design favors recoverability over optimistic success.

    • Store before attempting transport.
    • Reuse identity across every retry.
    • Validate context at the receiving boundary.
    • Surface uncertainty to the person doing the work.
    06 / THE BUILD

    A small stack keeps the reliability logic inspectable.
