01 / PURPOSE

What are we trying to do?

CaptureTrace explores one narrow engineering question: when a connected measuring tool sends a physical reading into a digital job form, how can the system prevent weak connectivity, retries, old clients, or unexpected context from silently corrupting the project record?

The guarantee

No measurement should be silently lost, written twice, converted without consent, or assigned to an incompatible field.

This is an independent browser simulation. It is designed to demonstrate reasoning about connected systems, not to reproduce or prescribe REEKON Tools' internal architecture.

02 / MENTAL MODEL

One pipeline, five independent scenarios

The scenario buttons are not a five-step workflow. You do not run Clean capture and then continue into Offline jobsite. Each button resets the workspace and performs a fresh run through the same pipeline.

THE PIPELINE

Steps that always happen

Capture, persist, deliver, validate, decide.

THE SCENARIOS

Conditions we change

Connectivity, acknowledgment, units, or contract version.

Think of it like testing the same car route under clear weather, a road closure, a repeated toll charge, the wrong fuel, and an outdated map. The route is shared; the disturbance changes.

03 / COMPLETE END-TO-END FLOW

Every step in one measurement journey

  1. The tool captures a reading.

    The synthetic CT-07 produces a value, unit, device sequence, and intended form field.

  2. The app creates an event envelope.

    It adds `event_id`, `device_id`, `captured_at`, job context, field context, sequence, and `measurement.v3`.

  3. The app stores the event locally.

    Persistence happens before transport. The measurement therefore remains recoverable during an outage.

  4. The app attempts delivery.

    Connected events send immediately. Offline events stay queued until reconnection.

  5. The receiver checks event identity.

    If the ID was accepted earlier, another delivery is a duplicate and cannot write twice.

  6. The receiver validates the contract.

    Schema version, units, field context, device, and sequence are checked before trust is granted.

  7. The receiver chooses an outcome.

    Accepted updates the form. Queued waits. Duplicate is suppressed. Review pauses for a human.

  8. The interface explains the outcome.

    The form, trace, counters, and downloadable report agree on what happened and why.

04 / INTERFACE MAP

How to read the demo screen

A

Connected tool

Shows the reading, unit, intended field, sequence, contract, and network state. Use Capture measurement for a manual event and Take offline to simulate connectivity.

B

Field workflow

Shows the job form. A trusted event fills its field. A questionable event is visibly marked for confirmation. Queued work appears in a local-storage banner.

C

Integrity trace

Explains each event decision with its ID and reason. Export report downloads the evidence after at least one event exists.

The five counters above the panels summarize captured, accepted, duplicate, review, and silently lost events. Silently lost should remain zero in every prepared scenario.

05 / SCENARIO REFERENCE

Exactly what each prepared run does

01

Clean capture

BASELINE
Setup
Connected app, expected units, current contract.
Action
Three identified events are captured and sent once.
Expected
All three are accepted and fill the form.
Proves
The normal path preserves identity and context.
02

Offline jobsite

TRANSPORT FAILURE
Setup
The app begins offline.
Action
Events are stored locally, then replayed in sequence after reconnection.
Expected
Queued events become accepted after replay; none disappear.
Proves
Local-first capture separates field work from network availability.
03

Lost acknowledgment

RETRY FAILURE
Setup
The receiver accepts an event, but the client does not receive confirmation.
Action
The client retries the exact same event ID.
Expected
One accepted value and one suppressed duplicate.
Proves
Idempotency makes uncertain delivery safe.
04

Wrong units

CONTEXT FAILURE
Setup
The form expects inches while the event contains millimeters.
Action
Transport succeeds and validation inspects the unit.
Expected
The value is held for unit confirmation and not trusted.
Proves
The system does not silently convert ambiguous input.
05

Old app contract

COMPATIBILITY FAILURE
Setup
An older app emits `measurement.v2`; the receiver requires v3.
Action
Delivery succeeds and schema validation detects the mismatch.
Expected
The event is held before it changes the form.
Proves
Version incompatibility is visible instead of silently misread.
06 / MANUAL EXPLORATION

What the two manual controls do

Capture measurement

Creates the next synthetic event for width, height, or depth. While connected, it is accepted. While offline, it is queued.

Take offline and Reconnect

Toggles the transport state. Reconnecting replays queued events in order. Manual exploration uses the same event and trace model as the prepared scenarios.

Reset

Clears events, fields, counters, queue state, and timers, then restores the connected baseline.

07 / EVIDENCE

What the downloadable handoff contains

After any event exists, Export report downloads a Markdown file with the job, final field decision, required next action, totals, measurement IDs, values, states, and reasons. A supervisor or engineer can review what happened without replaying the animation.

10 / GLOSSARY

Terms used in the demo

Event
A measurement plus identity, time, device, unit, field context, and contract version.
Outbox
Local storage for work that is captured but not yet confirmed by the receiver.
Idempotency
Repeating the same request produces no additional write after the first success.
Acknowledgment
The receiver's confirmation that it accepted an event.
Contract
The agreed shape and meaning of an event, such as `measurement.v3`.
Review
A visible hold state for input that reached the receiver but cannot be safely trusted automatically.
